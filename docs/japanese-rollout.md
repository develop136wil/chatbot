# 일본어 적용 안내

## 구현 범위

- 다섯 번째 언어 ja: 국기 선택·첫 화면·추천 질문·팁·음성 인식(ja-JP)·문의·오류·결과 더 보기.
- 일본어 질문 → 한국어 검색 키워드 → 기존 한국어 검색 인덱스 → 준비된 일본어 제목/본문.
- 응답 캐시는 언어별 분리. 동일 질문 재사용과 결과 더 보기는 추가 번역을 요구하지 않는다.
- 언어별 통계의 ja는 '일본어'로 표시한다. 국적이나 일본인 이용자 수를 의미하지 않는다.
- 한국의 사업명·원화·나이·조건을 보존하도록 번역 프롬프트에 명시한다.
- 기존 문서는 metadata.title_ja와 metadata.pre_summary_ja만 보완한다. 원문이 바뀌지 않았다면 임베딩·한국어 요약·이미 준비된 다른 번역을 다시 만들지 않는다.
- 실시간 번역 기본값은 계속 꺼져 있다. 일본어가 미완료인 자료는 미번역 안내와 한국어 원문으로 표시한다.

## 1. 통계 SQL 적용 (배포 전)

1. Vercel Production의 SUPABASE_URL과 같은 Supabase 프로젝트인지 확인한다. 이 대화에서 확인한 프로젝트 ref는 vlxxxpqyvrvcwffrpvid이다.
2. SQL Editor → New query.
3. supabase/20260921_japanese_language.sql의 전체 내용을 붙여넣고 Run.
4. 반환된 language_rule 안에 ja가 들어 있는지 확인한다.

기존 20260921_analytics.sql이 적용되어 있어야 한다. 새 설치도 기존 SQL 다음 일본어 SQL 순서다.
이 SQL은 언어 허용 CHECK 제약을 트랜잭션 안에서 교체한다. DROP 경고가 나올 수 있지만 행/테이블을 삭제하지 않고 RLS나 접근 권한도 완화하지 않는다.
기존 통계 기록을 지우거나 이전 analytics SQL을 수정해서 다시 적용할 필요는 없다.
SQL만 적용해도 기존 4개 언어 서비스는 계속 사용할 수 있다.

## 2. 코드 배포

코드를 GitHub에 반영하고 CI 성공을 확인한 다음 Production에 배포한다.
SQL 통합 테스트는 GitHub CI의 폐기 가능한 PostgreSQL에서 마이그레이션 반복 적용·일본어 집계·기존 권한을 검증한다.
새 키/추가 유료 모델은 필요하지 않다. 배포·운영 데이터 번역은 별도 실제 실행이 필요하며 로컬 테스트 완료와 구분한다.

## 3. 기존 문서 일본어 번역 준비

기본 브랜치에 코드가 반영되면 기존 Daily Content Indexing 예약 실행에서 이어서 처리한다.
현재 예약 시각은 매일 한국 시간 새벽 4시이며, 실제 시작은 지연될 수 있다.
급하지 않으면 자동 실행을 기다린다. 수동 Run workflow는 운영자가 원할 때만 실행한다.

변경 없는 문서의 누락 번역 보완은 기본 실행당 최대 20건이다.
선택 환경변수 INDEXER_TRANSLATION_BACKFILL_LIMIT으로 바꿀 수 있지만 필수 설정은 아니다.
부분 번역은 검증된 필드만 저장하고 다음 실행에서 누락 필드를 보완한다.
완료 문서는 건너뛰며, 원문·기존 번역·임베딩을 불필요하게 다시 만들지 않는다.

### 요청 제한과 번역 검증

- 인덱싱 번역 요청에만 Groq 속도 조절을 적용한다. 초기 기준은 이번 오류 로그의 분당 8,000토큰이며, 응답 헤더에서 더 낮은 한도가 확인되면 낮춘다.
- 토큰 추정량에 따른 간격과 공급자의 남은 토큰·재개 시간·Retry-After를 반영한다. 조직 내 다른 요청까지 통제하지는 않으므로 429가 절대 발생하지 않는다는 보장은 아니다.
- Groq 통신 재시도는 최대 2회 시도이며 SDK 중복 재시도를 끈다. 응답 형식 검증은 공급자별 최대 2회 시도다. 각 Groq 형식 시도에서 통신 재시도가 발생하면 총 호출 수는 최대 4회가 될 수 있다.
- 한 번의 요청 전 대기가 90초를 넘으면 기다리며 반복 호출하지 않고 해당 경로를 보류한다. 일일 한도·인증 오류는 해당 실행에서 공급자 호출을 중단한다.
- Gemini 대체 경로는 구조화된 JSON과 제목·본문을 검사하고, 빈 응답·JSON 오류·필드 누락·출력 잘림을 구분한다. 일시 오류는 최대 2회 시도하며 출력 잘림은 같은 예산으로 반복하지 않는다.
- 무료 모드 출력 상한은 그대로 유지한다. 긴 번역이 이 상한에 걸리면 실패로 남기고 다음 실행에서 다시 처리한다. 키 순환으로 한도를 우회하거나 유료 모델을 활성화하지 않는다.
- 형식 검증은 번역의 의미 정확성까지 보증하지 않는다.

### GitHub 실행 결과 읽는 방법

실행 Summary 표와 마지막 [Indexer Summary]를 함께 확인한다.

| 항목 | 뜻 |
|---|---|
| translations_attempted | 이번 실행에서 번역을 시도한 문서 |
| translations_completed | 필요한 번역이 완성되고 DB 저장까지 성공한 문서 |
| translations_failed | 번역 보완 실패 문서(보완 결과 저장 실패 포함) |
| translations_deferred | 20건 처리량 제한으로 이번 실행에서 미시도한 문서 |
| translations_pending | 확인된 번역 미완료 합계 |

- status=complete: 번역 미완료가 0건이고 문서·카테고리·삭제·캐시 처리 오류가 없다.
- status=in_progress: 실제 오류 없이 처리량 제한으로 남은 문서만 있다. 종료 코드는 0이지만 **전체 번역 완료는 아니다.**
- status=failed: 번역 실패 또는 저장·조회·캐시 등 실제 오류가 있다. 종료 코드는 1이며 로그 확인이 필요하다.

예를 들어 155건 중 번역 20건을 시도하여 19건 완료·1건 실패·135건 미시도라면,
translations_pending=136, translations_failed=1, translations_deferred=135이고 status=failed다.
20건 모두 성공하고 135건만 미시도라면 status=in_progress다.
카테고리 조회 등에 실패했다면 미완료 합계가 전체 DB 상태를 대표하지 못하므로 오류를 먼저 해결한다.

이번 개선에는 추가 SQL이나 새 환경변수 설정이 필요하지 않다.
완료 시점은 남은 문서 수·번역량·제공량 제한에 따라 달라지므로 특정 날짜까지 완료된다고 보장하지 않는다.

## 4. 운영 완료 판정

supabase/20260921_japanese_verify.sql의 첫 SELECT를 단독 실행한다.

- total_documents > 0
- japanese_ready = total_documents
- japanese_pending = 0

이는 문자열 필드 준비 여부 검사이며 번역의 의미 정확성까지 보증하지 않는다.
인덱서 마지막 요약이 complete, failed_pages=0, failed_categories=0, translations_pending=0인지 확인한다.
캐시 버전 갱신·정리 실패도 없어야 한다.

Production에서 日本語를 선택한 뒤 아래 항목을 확인한다.

1. 韓国の児童手当 / 乳幼児の発達検査 질문에 일본어 카드가 나오는지.
2. 한국어 원문과 금액·월령·자격 조건이 일치하는지. 중요한 안내는 일본어 검수가 권장된다.
3. 같은 질문을 반복했을 때 캐시를 쓰고, 結果をもっと見る가 다음 결과로 이어지는지.
4. 통계가 활성화된 상태에서 일본어 요청 후 대시보드에 '일본어'가 잡히는지.
5. 한국어·영어·베트남어·중국어 이용이 유지되는지.

배포 전에는 실제 운영 데이터 번역 완료나 운영 통계 수집 성공을 주장하지 않는다.
