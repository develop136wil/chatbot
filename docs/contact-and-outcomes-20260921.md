## 이번 구현 범위

- 수신 주소: chanyoung@devleop136.com (사용자 제공 철자 그대로).
- 큰 평가 패널 대신 접힌 ‘문의 · 불편 신고’ 메뉴. 첫 안내와 답변, 오류 화면에서 접근.
- 메뉴를 열면 주소 링크, 복사 버튼, 개인정보 주의 안내. 메일 앱은 사용자가 링크를 눌러 연다.
- mailto에는 주소와 고정된 언어별 제목만 넣고, 질문·답변·대화 기록을 자동 첨부하지 않는다.
- 메일 앱 미설정 시 주소 복사 사용. 클립보드 권한 거부 시 수동 복사 안내.
- 메일 작성 창 열기/주소 복사는 발송·수신 확인이 아니다. 메일함 실수신은 미검증.
- 기존 /feedback은 410으로 종료하며 Notion에 쓰지 않는다. 오래 열린 탭은 새로고침해야 한다.
- 기존 Notion 피드백 데이터는 삭제하지 않는다. 질문 로그, 검색·캐시·AI 한도 로직은 변경하지 않는다.
- 아래는 제안이며 통계 이벤트 수집, 신규 DB, 대시보드는 아직 구현하지 않았다.

## 현재 질문 로그의 한계

worker.py의 ENABLE_NOTION_QUERY_LOGS 기본값은 false이다. 운영 환경의 활성화 여부는 별도 확인 필요.
활성화 시 검색·답변 생성 성공 경로에서 질문 원문, 분류, 키워드를 Notion에 기록한다.
그러나 캐시 반환, 더 보기, 검색 결과 없음, 실패 등이 같은 경로로 수집되지 않는다.
저장은 asyncio.create_task로 분리되어 요청 종료 전에 저장 완료를 보장하지 않는다.
따라서 Notion 차트는 ‘기록된 질문의 분포’에는 쓸 수 있지만 전체 이용량, 성공률, 실제 이용자 수의 근거는 아니다.
worker의 로그 DB ID는 현재 하드코딩되어 있어 환경변수 문서와도 차이가 있다.
기존 자료를 신규 전체 수집 통계와 섞거나 누락분을 추정해 실적으로 표시하지 않는다.

## 공유회용 월간 1쪽 보고서 제안

| 항목 | 지표와 분모 | 권장 표현 |
| --- | --- | --- |
| 이용 규모 | 중복 제거한 신규 정보 질문 수, 대화 세션 수 | 월별 추이; 세션을 실제 인원으로 부르지 않음 |
| 관심 분야 | 신규 정보 질문을 5개 분야 + 복합/미분류로 단일 분류 | 가로 막대; 분류 누락도 표시 |
| 이용 경로 | 허용 목록의 유입 경로(기관 홈페이지·QR 등), 추천 질문/직접 입력 | 출처 미상 포함; 출처 링크 사전 설계 필요 |
| 접근성 | 선택 언어별 신규 질문 수 | 국적·외국인 수로 해석하지 않음 |
| 정보 연결 | 원문 링크를 1회 이상 누른 세션 / 결과 카드가 표시된 세션 | 자료 원문 연결률; 신청·수혜율과 구분 |
| 신뢰성 | 결과 있음 / 결과 없음 / 기술 오류 / 추가 질문 필요 | 모든 신규 정보 질문을 분모로 하고 합계 대조 |
| 이용 속도 | 요청부터 화면 표시까지 중앙값과 95백분위 | 캐시/신규 검색을 분리, 실패 응답 별도 |
| 효율 | 캐시 적중 / 캐시 조회 대상 요청 | 토큰 절감률은 실제 사용량이 있을 때만 산정 |

추천 발표 구조: 어떤 수요가 있었나 → 자료에 얼마나 연결했나 → 실패와 대기시간이 어떻게 개선됐나.
수치 옆에 기간, 표본 수, 정의, 누락률, 배포 버전 변경점을 적는다.
개선 전후 비교는 같은 기준으로 집계된 기간만 사용한다.
품질은 고정 평가 질문과 정기 표본 검토로 별도 측정하고, 검색 결과 존재율을 정확도로 부르지 않는다.
실제 신청·수혜 성과는 기관의 별도 확인이나 동의 기반 조사 없이는 주장하지 않는다.

## 수집 설계 제안 (아직 미구현)

- 신규 질문 / 더 보기 / 초기화 / 명확화 응답 / 재시도를 분리한다.
- 요청 ID와 이벤트 종류를 묶어 중복을 제거한다. 재시도는 원 요청과 연결하고 시도 수는 별도로 보관한다.
- 익명 임시 세션은 사용자 계정·실제 사람과 다르다. IP 기반 방문자 식별은 하지 않는다.
- 기본 필드: 발생 시각, 사건 종류, 언어, 정규화 분야, 결과 상태, 처리시간, 캐시 여부, 유입 코드, 배포 환경/버전.
- 원문 질문, 답변, 이름, 연락처, 전체 URL은 성과 집계에 기본 수집하지 않는다.
- 분야는 기존 검색 분류/결과 메타데이터 활용. 추가 AI 호출 없이 복합·미분류를 명시한다.
- 선택 언어/분류/유입은 조작 가능하거나 추정된 값임을 고려한다.
- 운영 데이터만 보고서에 포함하며 테스트/개발/봇 판별 기준과 한계를 문서화한다.
- UTC 저장, Asia/Seoul 월 경계로 집계. 일별 원시 이벤트 수와 집계 합계를 대조한다.
- 서버 이벤트는 캐시 포함 공통 완료 지점에서 수집하고, 저장 확인·시간 제한·실패 계수를 둔다.
- 클릭 이벤트는 조작 방지 검증과 속도 제한을 두고, 수집 실패가 검색 응답을 막지 않도록 한다.
- 임의의 fire-and-forget은 완전 수집의 근거가 아니다. 재전송 가능한 지속 저장과 중복 방지가 필요하다.
- 공개 보고서는 소수 집단의 세부 교차분석과 자유서술 원문을 제외한다.
- 도입 전에 보관 기간, 접근 권한, 이용자 고지, 저장소를 확정한다.

## 단계와 승인 지점

1. 지금: 이메일 UI만 단순화, 기존 질문 로그 보존.
2. 다음: 지표 정의와 운영 로그 활성 상태 확인. 과거 Notion 기록은 참고 통계로만 표시.
3. 수집: 별도 통계 저장소 승인 후 구현. 기존 검색/캐시 테이블에 통계 데이터를 섞지 않는다.
   Supabase 별도 이벤트/집계 테이블이 관리상 적합하지만 새 SQL 적용이 필요하다.
   현재 사용자가 SQL 적용하기 어려우므로 이번에는 신규 테이블을 요구하거나 생성하지 않는다.
   임시 로그 내보내기를 쓰려면 보관 기간·내보내기 가능 여부부터 확인하며, 영구 성과 저장소라고 가정하지 않는다.
4. 검증: 캐시·신규 검색·실패·다국어·재시도·더 보기·원문 클릭을 테스트하고 집계 건수를 대조.
5. 보고: 월별 집계 CSV와 공유회용 1쪽 보고서를 생성. Notion은 필요하면 완성된 월간 요약만 게시.

자동 보고서에 AI 요약을 필수로 넣지 않는다. 계산과 정적 차트로 만들면 이 기능 자체에 AI 토큰이 들지 않는다.

## 구현 검증

- Python 회귀 테스트 115개, 프런트엔드 테스트 102개 통과.
- 종료된 평가 폼 전용 테스트는 이메일 문의 계약 테스트로 교체했다.
- 네 언어의 mailto 주소/제목, 대화 미첨부, 복사 성공·권한 거부, 중복 메뉴 방지, 오류 화면 접근 검증.
- 테스트는 모의 DOM 기반이며 실제 모바일 배치와 이메일 실수신을 검증한 것은 아니다.
- 검색·캐시 관련 소스와 Supabase 스키마는 변경하지 않았다.
