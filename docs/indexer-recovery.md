# 인덱싱 복구·캐시·요청 제한 보완

작업일: 2026-09-20

기준 커밋: c8b1468
상태: 로컬 구현/오프라인 검증 완료. 이번 변경의 커밋·푸시·배포 미실행.

## 완료 판정

run_indexing()은 성공하면 IndexingReport를 반환합니다.
미완료이면 보고서를 포함하는 IndexingIncomplete 예외를 발생시킵니다.
CLI는 미완료일 때 종료 코드 1을 반환하여 GitHub Actions에 실패가 드러납니다.
호출하던 main.py 스케줄러의 기존 예외 처리와 호환됩니다.

로그의 [Indexer Summary]에 다음 수치를 남깁니다.

- discovered: 조회가 완료된 카테고리에서 발견한 페이지 수
- updated / skipped: 저장 성공 / 내용·카테고리·번역이 완전해 건너뛴 페이지 수
- failed_pages / failed_categories: 페이지 처리 / 카테고리 전체 조회·처리 실패 수
- deleted / failed_deletions: 삭제 성공 / 삭제 실패·보류 수
- translations_pending: 저장됐으나 EN/VI/ZH 제목·요약이 모두 준비되지 않은 페이지 수
- cache_refresh_failed / cache_marker_failures: 캐시 버전 갱신 실패 / 재시도 표시 정리 실패
- cleanup_failed / setup_failed: 만료 캐시 정리 실패 / 초기화·기존 상태 로드 실패

실패나 보류가 하나라도 있으면 status=incomplete입니다.
전체 카테고리 조회 실패 시 discovered는 전체 Notion 문서 수가 아닙니다.
번역 보류는 updated와 겹치는 부분 집합이며 별도 문서 수로 합산하면 안 됩니다.
정상 종료는 프로그램의 검증 기준을 통과했다는 의미이며 번역 내용의 원어민 검수를 뜻하지 않습니다.

## 부분 실패와 캐시 복구

- 다른 카테고리에서 오류가 나도 이미 저장된 문서의 캐시 범위는 갱신합니다.
- 기존 문서 삭제는 조회/처리 오류가 없는 경우에만 수행합니다.
- 새 SQL 없이 기존 metadata JSON에 cache_invalidation_pending_scopes를 저장합니다.
- 캐시 갱신이 실패하면 이 표시를 유지합니다. 다음 실행은 변경 없는 문서를
  AI로 다시 처리하지 않고 보류된 캐시 버전 갱신을 재시도합니다.
- 갱신에 성공한 후 보류 표시를 제거합니다. 제거 실패도 미완료로 표시합니다.
- 카테고리 이동은 수정일이 같아도 재처리하며 이전/새 카테고리를 함께 갱신합니다.
- 삭제 후보는 기존 행에 재시도 표시를 남기고 사전 캐시 갱신이 성공해야 삭제합니다.
- DB 상태 읽기 실패를 빈 DB로 간주하지 않습니다. 초기화 실패로 중단합니다.
- 상태 조회는 500행 단위로 페이지를 나눠 읽습니다.
- Notion 응답에 results/has_more가 없거나 커서가 반복되면 조회 실패로 처리해 삭제를 막습니다.
- Daily Content Indexing에 concurrency 그룹을 추가했습니다.
  진행 중인 실행을 취소하지 않고 동일 workflow의 중복 실행을 직렬화합니다.
  별도로 시작한 로컬 인덱서까지 막는 분산 잠금은 아닙니다.

비용 영향: 변경 문서의 보류 표시 제거 등에 DB 요청이 추가됩니다.
보류된 캐시 갱신만 재시도할 때는 추가 요약·번역·임베딩 요청을 하지 않습니다.
내용 변경 또는 번역 미완료 문서의 재처리는 기존처럼 AI 한도를 사용할 수 있습니다.
강제 전체 재색인·전체 캐시 비우기는 추가하지 않았습니다.

한계: 문서 저장과 캐시 버전 갱신은 서로 다른 DB 요청입니다.
동시 검색/인덱싱 전 과정을 하나의 트랜잭션으로 묶은 것은 아니며,
특히 삭제 중 프로세스 강제 종료 같은 분산 경합까지 완전히 해결했다고 보장하지 않습니다.
캐시 버전 갱신 자체가 실패하면 보류가 복구될 때까지 오래된 캐시가 남을 수 있습니다.
따라서 incomplete 로그를 무시하지 않아야 합니다.

## 요청 제한

기존 Redis GET → 비교 → INCR 분리를 Lua EVAL 한 번으로 묶었습니다.
Redis Lua의 원자 실행 보장은 [Redis 공식 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)를 참고했습니다.
고정 스크립트에 key/limit/window를 인자로 전달합니다.
Redis 실패 시 기존 잠금 기반 메모리 제한으로 전환합니다.
Redis가 명시적으로 거절한 요청을 메모리 제한으로 우회하지 않습니다.

실제 Redis 서버는 사용하지 않았습니다. 테스트는 원자 호출 계약 및 모의 결과,
실제 Python 메모리 제한 함수의 동시 요청 처리까지 검증했습니다.
메모리 제한은 프로세스 단위이고 일일 한도는 세션 단위입니다.
계정 전체 비용 상한이나 여러 서버 인스턴스 전체의 강제 한도를 보장하지 않습니다.

## 오프라인 전송

직접 전송·명확화 버튼·추천 질문·더 보기·오류 재시도 진입점에서
navigator.onLine === false이면 요청 생성 전 차단합니다.
입력 내용과 기존 문맥을 유지합니다. 재연결만으로 자동 전송하지 않습니다.
첫 화면 및 언어 변경에서도 오프라인 안내와 입력 잠금을 동기화합니다.
navigator.onLine이 true인 실제 통신 장애는 기존 요청 오류/수동 재시도 경로를 사용합니다.
