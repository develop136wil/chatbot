한계: 서명된 브라우저 세션 기반 제한이다. 쿠키 삭제/다중 세션/동시 요청을

## 프로세스 내 요청 제한 기록

- 마지막 허용 요청 시각 + 해당 기능의 제한 창으로 만료 시각을 보관한다.
- 요청이 들어왔을 때 최대 60초 간격으로 만료 기록을 정리한다.
  요청 없는 프로세스에서 별도 타이머를 구동하지 않는다.
- 요청/만료 맵 수정과 정리는 동일 asyncio 잠금 안에서 수행한다.
- 차단된 요청은 기록 만료를 연장하지 않는다.
- chat 60초, feedback 300초를 개별 유지한다.
- 프로세스당 최대 10,000개의 기능/IP 조합만 보관한다.
  용량 도달 시 만료 항목을 먼저 정리하고, 여전히 가득 차면 새로운 조합에
  HTTP 429 + Retry-After: 60을 반환한다. 활성 카운터를 지워서 우회시키지 않는다.
- 정리 스캔은 최대 10,000개로 제한된다. Redis 제한 정책은 바꾸지 않는다.

## 기존 작업 결과 재조회

질문 POST에서 작업 ID를 받은 뒤 조회 실패/시간 초과/잘못된 응답/렌더링 실패가
발생하면 재시도 버튼은 해당 작업 ID에 대한 GET만 실행한다.
KO/EN/VI/ZH에서 일반 재전송과 구분되는 '결과 다시 확인' 문구를 제공한다.

- 반복 실패 후에도 ID 유지. 자동으로 새 질문 POST를 만들지 않는다.
- 429 Retry-After 준수, 오프라인/중복 클릭/오래된 버튼 방지 유지.
- 결과가 명시적인 작업 실패(status=error)이고 재시도 가능할 때만 기존 정책대로
  사용자의 클릭으로 새 작업을 접수한다. provider_limit의 재시도 금지는 유지한다.
- 404/410은 조회 불가 안내만 표시하고 새 질문을 자동 전송하지 않는다.
- 폴링 대기의 취소는 즉시 타이머와 리스너를 정리한다.
- 기존 작업 ID는 메모리에만 보관하며 새로고침 후 복구 기능은 추가하지 않는다.

한계: 최초 POST 응답 자체가 끊겨 작업 ID를 받지 못한 경우의 중복 방지는
해결하지 않는다. 별도의 서버 멱등성 설계가 필요하다.
현재 API는 결과 키가 없으면 pending을 반환하므로 실제 만료와 아직 처리 중인
상태를 구별하지 못한다. 조회는 120초 제한 후 안내하며 자동 재접수하지 않는다.
