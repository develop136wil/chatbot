## 우선 수정: 정확성·장애·비용 통제

### P1-01. DB 검색 장애가 ‘관련 정보 없음’으로 장기 캐시될 수 있음 — 재현 확인

- 근거: `utils.py:2235`, `utils.py:2271` 검색 예외를 출력한 뒤 빈 목록 반환. `worker.py:102`는 빈 목록을 정상적인 검색 결과 없음으로 간주하고 응답 캐시 저장.
- 가짜 DB에서 RPC 예외를 발생시켰을 때 `status=complete`인 결과 없음 응답의 캐시 저장 호출을 확인했습니다.
- 기본 TTL은 7일이나 30일이 아니라 **90일(7,776,000초)**입니다. 관련 범위 버전 변경이나 정리 전까지 잘못된 빈 답변을 재사용할 가능성이 있습니다.
- 수정 방향: DB/임베딩 실패와 실제 검색 0건을 분리하고 실패 응답 캐시를 금지. 검색 일부만 성공한 경우도 캐시 허용 여부를 명확하게 구분.

### P1-02. 연령·대상 조건과 후속 질문 문맥이 실제 검색에 충분히 전달되지 않음 — 코드 확인 및 연령 필터 재현

- 근거: `main.py:535` 작업에는 분석 결과 중 카테고리만 전달. `worker.py:93`의 검색 입력은 `{"category": ai_category}`뿐입니다. AI가 추출한 `age`, `sub_category`, `keywords`가 소실됩니다.
- `utils.py:2261` 이후 연령 필터는 전체 검색 분기에만 존재합니다. 카테고리 결과가 3개 이상이면 연령 필터 없이 반환합니다. 연령 필터 결과가 0개여도 기존 결과를 다시 유지합니다.
- 36개월 조건에 0~12개월 문서 3건을 주입했을 때 부적합한 3건 모두 반환됨을 확인했습니다.
- `chat_history`는 의도 분석과 job_data에 존재하지만 worker의 검색·랭킹은 현재 질문만 사용합니다. ‘그중에 무료인 것은?’ 같은 질문을 독립적인 검색 질문으로 재작성하는 경로가 없습니다.
- 수정 방향: 검증된 분석 조건 전체 전달, 모든 검색 경로에서 일관된 조건 적용, 문맥 의존 질문만 제한적으로 독립 질문으로 변환. 조건 외 결과는 적합한 혜택처럼 표시하지 않기.

### P1-03. 인덱싱 실패·보류가 GitHub Actions 성공으로 보일 수 있음 — 재현 확인

### P1-04. 부분 인덱싱 성공 후 오류가 발생하면 캐시 무효화 누락 — 재현 확인

### P1-05. 캐시 범위 판정이 실제 검색 범위와 다를 수 있음 — 재현 확인

- 근거: `utils.py:443`은 결과 카테고리와 AI 카테고리 존재 여부만 보고 범위를 만듭니다. `search_supabase_async()`가 전체 검색으로 전환했는지는 전달되지 않습니다.
- 예: AI가 `welfare`로 분류해 전체 검색을 했으나 결과가 가족 지원에만 있으면 `__all__` 범위가 빠집니다. 다른 카테고리에 더 적합한 문서가 생겨도 이 캐시가 살아남을 수 있습니다.
- 재현에서 비표준 `welfare` 카테고리를 넣으면 전역 범위가 포함되지 않았습니다.
- 검색 이후 캐시 저장 직전에 범위 버전을 조회하므로 인덱싱과 동시 실행 시 구자료에 신버전을 붙이는 경합 가능성도 있습니다. 이 동시 실행 문제는 코드 위험 분석이며 실환경 장애를 관측한 것은 아닙니다.
- 수정 방향: 실제 검색한 범위와 데이터 버전을 결과와 함께 전달. 검색 전후 버전이 바뀌면 캐시 저장을 생략/재시도.

### P1-06. 무료 전용 플래그는 과금 차단 또는 전체 서비스 사용량 상한이 아님 — 코드 확인

- `FREE_TIER_ONLY`는 키 순환 제한, 일부 출력 제한 등을 적용하지만 공급자 계정이 Free/Paid인지 확인하지 않습니다. 유료 계정의 키를 넣으면 같은 요청이 과금될 수 있습니다.

- 무료 제한은 인덱싱 전체와 모든 Groq 호출에 공통 예산으로 적용되지 않습니다.
- 수정 방향: 공급자 콘솔의 무료 플랜/결제 상태 확인과 별개로, DB 등을 이용한 원자적인 전체 일일 예산, 입력/출력 토큰 상한, 한도 도달 시 동작을 정하기.
- **이전의 ‘설정만으로 추가 청구 없이 보장된다’는 설명은 과도했습니다. 코드만으로 비용 0원을 보장할 수 없습니다.** 이번 감사에서는 결제 설정을 조회하지 않았습니다.

## 다음 수정: 다국어·사용자 기능·성능

### P2-01. 번역 폴백의 4,096토큰 요청이 실제로는 400토큰으로 제한됨 — 재현 확인

- 가짜 Gemini 클라이언트에서 실제 전달값 400을 확인했습니다. 긴 원문에서는 JSON이 잘리거나 빈 응답이 나올 위험이 큽니다.
- 현재 155개 번역 필드는 모두 존재합니다. 이는 앞으로의 갱신/폴백 실패 위험입니다.
- 수정 방향: 작업별 예산 분리, 필요한 언어만 재시도, 출력 종료 사유/구조 검증. 무료 한도를 초과하면 보류 처리하며 완성된 번역으로 간주하지 않기.

### P2-02. JSON Object Mode만 적용되어 필드 검증과 오류 복구가 불완전함 — 재현 확인

- `utils.py:1093`은 `json_object`이며 JSON Schema가 아닙니다. `age="24"`, `category="null"`을 그대로 수용함을 재현했습니다.
- 프롬프트에 유효 카테고리 목록이 없고 모델이 볼 수 없는 `see utils.py rules`를 참조합니다.
- Gemini 의도 분석 폴백에는 JSON MIME/schema가 없고, Groq가 깨진 JSON 문자열을 돌려주면 Gemini 재시도 없이 규칙 대체로 갑니다.
- `FreeTierQuotaExceeded`는 규칙 대체 대신 error를 반환합니다. 임베딩은 항상 Gemini를 요구합니다. **AI/임베딩 없이 계속 검색하는 완전한 비AI 대체 경로는 없습니다.**
- 수정 방향: 필드 타입·허용 카테고리·null 정규화, 구조화 출력, 실패 원인별 분기. 실제 비AI 검색이 필요하면 별도의 키워드 SQL 경로 설계.

### P2-03. 영문 등 Vercel 응답 카드의 버튼이 한국어로 남음 — 코드/JavaScript 확인

- `utils.py:1995` 카드 버튼 텍스트는 한국어 고정입니다.

### P2-04. 피드백이 Vercel에서 표시되지 않으며 표시 경로도 오류 가능 — 코드/JavaScript 확인

### P2-06. 지연 상한과 재시도 예산이 요청 전체에 걸쳐 통제되지 않음 — 일부 재현, 일부 코드 확인

- 동기 `generate_content_safe(timeout=...)`의 timeout은 호출에 전달되지 않습니다. 내부 5회 × 외부 최대 5회 재시도가 가능합니다.
- 설치된 Groq SDK의 기본 재시도는 2회, 기본 read timeout은 60초입니다. 앱의 재시도와 중첩될 수 있습니다. 실제 Vercel SDK 버전은 고정하지 않았습니다.
- 키워드 확장은 요청마다 새 AsyncGroq를 만들고 닫지 않습니다. Supabase Secret 캐시도 매 요청마다 HTTP 클라이언트를 새로 만듭니다.
- 프런트엔드 45초 중단은 서버 AI 작업 취소를 보장하지 않습니다. 프로세스 executor의 임베딩 timeout도 이미 실행 중인 동기 호출을 중단하지 못합니다.
- 키워드 확장은 GPT-OSS에 100토큰만 주고 reasoning 설정과 종료 사유 확인이 없어 새 모델의 완성된 출력 여부를 실제 평가해야 합니다.
- 수정 방향: 공유 연결, 요청 전체 시간/호출 예산, 실패 유형별 재시도, 단계별 시간/토큰 관측. 현재 실제 AI 응답 시간의 p50/p95는 측정하지 않았습니다.

### P2-07. ‘더 보여줘’ 자연어 인식과 페이지 누락 처리의 빈틈 — 코드 확인

- 프런트는 정해진 SHOW_MORE_KEYWORDS 문구에만 결과 ID를 보내므로 ‘그 다음 것도 보여줘’처럼 AI가 더 보기로 인식할 수 있는 다른 표현은 상태가 없어 일반 검색으로 흘러갈 수 있습니다.
- 베트남어 안내의 `Tiếp theo`가 목록과 정확히 일치하는지도 통합 테스트 대상입니다.
- 결과 ID 중 삭제된 문서가 있으면 `build_show_more_response()`가 0개 카드를 추가 정보로 표시하고 shown_count를 건너뛸 수 있습니다.
- 수정 방향: 더 보기 버튼/명시적 action 지원, 결과 상태 전달 일관화, 사라진 ID를 감안한 다음 페이지 보충.

### P2-08. 캐시 재사용 범위와 관측이 제한적 — 코드 확인

- 정상 독립 질문과 직전 동일 질문의 키/조회 자격은 오프라인 검사 통과했습니다.
- 저장은 초기 독립 질문만 허용합니다. 문맥 중 처음 검색한 질문은 저장되지 않아 반복해도 캐시가 없을 수 있습니다. 문맥 답변을 공용 캐시에 무조건 저장하면 다른 사용자의 답변이 섞이므로 개선 시 주의가 필요합니다.
- 의미 기반 캐시 함수는 남아 있으나 현재 worker 흐름에서 호출되지 않습니다. 따라서 ‘비슷한 질문도 자동 재사용’하는 것으로 해석하면 안 됩니다.
- cache_version은 v2로 고정되어 모델·렌더러 변경 시 기존 HTML 캐시를 자동 갱신하지 않습니다.
- 캐시 에러는 프로세스에서 한 번만 로그에 나오고 hit/miss 원인 및 비율 집계가 없습니다. 현재 행 1개라는 사실만으로 전체 적중률을 추정할 수 없습니다.

## 보안·배포·유지보수 보완

1. `ChatRequest.chat_history: List[dict]`는 역할/본문 타입과 항목 크기를 검증하지 않습니다. `[{}]`를 전달하면 의도 분석의 try 밖에서 KeyError가 발생함을 재현했습니다. 과도하게 긴 내역도 검증 단계에서 제한되지 않습니다.
2. `/debug`는 기본 off지만 on으로 켜면 관리자 인증 없이 외부 서비스 진단/임베딩 호출이 가능합니다. 이번에는 운영 `/debug`를 호출하지 않았습니다.
3. `/health`는 고정 ok라 DB/AI 장애와 무관합니다. 준비 상태, 최근 인덱싱 완료/실패, 배포 SHA 같은 운영 관측 지표가 없습니다.
4. `/admin/clear_cache`는 Redis만 지웁니다. Vercel의 Supabase 응답 캐시는 대상이 아니고 `extract:*` 패턴은 실제 `extract_v2:*`와 다릅니다. 관리자 키를 쿼리 문자열로도 받습니다.
5. SessionMiddleware는 `https_only=True`를 명시하지 않았습니다. 쿠키 제한/보호는 배포 프록시와 함께 점검해야 합니다. 메모리 rate-limit 테이블은 다른 IP의 만료된 항목을 정리하지 않습니다.
6. `/get_result/{job_id}`는 세션 소유권 확인이 없습니다. UUID 추측은 어렵지만 ID를 얻으면 다른 결과를 조회할 수 있습니다. 현재 Vercel 직접 응답 경로에는 영향이 제한적입니다.
7. Redis 연결 객체 존재를 건강 상태로 간주하므로 비Vercel 환경에서 Redis가 끊어졌을 때 push 오류가 자동 직접 실행으로 전환되지 않습니다. Redis 미설정도 localhost 객체가 생성될 수 있습니다.
8. `run_indexer.py` DB ID는 하드코딩되어 `.env.example`의 NOTION_DB_* 설정을 따르지 않습니다. 의료/재활 기본 ID가 utils와 다릅니다. 현재 실제 사용 중인 인덱서 DB는 이번 실조회로 정상 확인했습니다.
9. DB 상태 로드는 limit(5000) 한 번뿐이며 실제 Supabase 행 제한에 대한 페이지 순회가 없습니다. 현재 155개에서는 문제 없지만 규모 증가 시 누락/재처리 위험이 있습니다.
10. 인덱서는 Notion 페이지 속성만 가져옵니다. 페이지 내부 블록 본문은 가져오지 않습니다. 실제 운영자가 본문 블록에도 정보를 기록한다면 현재 검색 반영 범위 밖입니다.
11. 번역 보완만 필요한 문서도 기존 임베딩을 다시 생성합니다. 변하지 않은 원문에 불필요한 토큰이 듭니다.
12. requirements는 버전 고정/lock 없이 설치합니다. 로컬 Python은 3.14, Actions는 3.11. 로컬 notion-client는 1.0.0으로 요구조건 >=2.0.0과 다릅니다. pip check 통과는 requirements 일치 검증이 아닙니다.
13. `hybrid_search_v3`와 site_pages 생성 SQL이 저장소에 없어 신규 프로젝트를 동일하게 복구하기 어렵습니다. 캐시 테이블 SQL 두 개만 존재합니다.
14. 자동 회귀 테스트/테스트 CI가 없으며 `.gitignore`는 test_*.py를 무시합니다. node_modules도 이미 Git 추적되어 있습니다.
15. README는 Llama 3.3, 키 순환, Redis 장애 대체 동작 등 실제와 다릅니다. 동기 helper에는 접근 불가인 llama-3.1-8b-instant도 남아 있습니다. 이는 현재 Vercel 정상 비동기 경로의 모델과는 다릅니다.
16. CDN marked는 버전 미고정이며 프런트 일부 문자열/공유/시간 초과는 한국어 고정입니다. DOMPurify가 로드되지 않을 때 텍스트로 처리하는 보호는 존재합니다.

## 확인된 보호 및 정상 구현

- 사용자 텍스트는 textContent로 렌더링. 카드 본문/제목은 서버에서 이스케이프하고 URL 프로토콜을 제한. 모의 XSS 문자열 검사 통과.
- 클라이언트에서 DOMPurify를 적용. 로드 실패 시 HTML을 텍스트화하는 경로가 있음.
- 캐시 SQL에 RLS 활성화와 anon/authenticated 권한 회수, service_role 접근 권한 명시.
- 캐시 언어 분리, 공백 정규화, 직전 동일 질문 조회 조건은 정상.
- Notion 페이지 조회가 불완전하면 삭제 단계를 건너뛰는 데이터 손실 방지 코드가 있음.
- 무료 모드에서 Gemini 키 순환 비활성화, 실시간 번역 기본 off, Notion 질문 원문 로그 기본 off.
- Git 추적 파일 목록에서 .env는 제외. 비밀값은 감사 출력/보고서에 기록하지 않음.

## 검증 범위와 한계

- 실제 확인: 웹 GET, 정적 파일 비교, 공개 GitHub API, 운영 reference와 일치하는 로컬 키의 DB GET, Notion 5개 DB 읽기 조회(POST query), Groq 모델 목록 GET.
- 오프라인 확인: Python 5개 파일 문법, JavaScript 문법, pip check, 실제 함수 AST를 가짜 서비스로 실행한 정상 4개 묶음 및 결함 10개 묶음 재현. 추가 JS 검사에서 피드백 정의와 완료 경로 누락 확인.
- 실제 AI 생성 호출, 인덱싱 실행, DB 쓰기/캐시 삭제, 이메일 발송, 배포/푸시를 하지 않았습니다.
- Vercel의 실제 환경변수/백엔드 배포 SHA/결제 계정, Supabase 대시보드 내부 설정, 사용자별 대화 E2E, 모바일 실화면, 번역 의미 전수 비교, 부하 및 보안 침투 테스트는 이번 검증 범위 밖입니다.
- 따라서 ‘현재 챗봇 질문이 항상 성공한다’, ‘무료 과금이 절대 없다’, ‘4개 언어가 완전 호환된다’, ‘15~30초가 보장된다’고 결론 내릴 수 없습니다.

1. DB 장애 응답 캐시 금지 → 인덱싱 실패 판정/무효화 수정.
2. 연령·대상·대화 조건 전달과 실제 검색 범위 기반 캐시 수정.
